# H9: мягкое сопоставление query edge с KG-путём

Дата фиксации: 15.11.2026. Ветка задачи #19.

## Мотивация

На FactKG dev SHA-256 ranks 500–999 H8 покрыл 219/767 (28,55%)
авторских evidence paths, B1 — 416/767 (54,24%), а весь уже
собранный KG pool содержит 610/767 (79,53%). Разбиение по
длине показало:

| Длина evidence path | Всего | Есть в KG pool | H8 | B1 |
|---:|---:|---:|---:|---:|
| 1 | 517 | 456 | 219 | 387 |
| 2 | 242 | 152 | 0 | 29 |
| 3 | 8 | 2 | 0 | 0 |

H8 сопоставляет каждое query edge только с одним KG edge.
При этом извлечённый LLM граф может свернуть композицию
отношений в одно ребро, например `film --producer is from--> city`,
которому в KG соответствует `film --producer--> person --birthPlace--> city`.

## Гипотеза

**H9.** Если разрешить query edge сопоставляться не только с
одним KG edge, но и с направленным путём длины 2, matcher
покроет больше эталонных FactKG paths и снизит UNKNOWN относительно
H8 без расширения entity candidates.

## Алгоритм

1. Query graph, entity candidates и KG pool берутся из того же
   однопроходного extraction, что и для H8.
2. Для каждой пары кандидатов концев query edge перечисляются
   направленные простые KG paths длины 1–2. Повтор одной тройки
   и промежуточный узел, равный концу пути, запрещены.
3. Query edge и KG path вербализуются с концами, отношениями и
   промежуточным узлом. Их cosine считает тот же
   `sentence-transformers/all-MiniLM-L6-v2`.
4. Скор path: `cosine(query_edge, kg_path) - 0.1 * (length - 1)`.
   Штраф `0.1` и максимальная длина 2 фиксируются до запуска.
5. Итоговая mapping cost не меняет веса H8:
   `0.3 * mean(node_distance) + 0.7 * mean(1 - best_path_score)`.
6. Beam width 64, инъективность, 80% node coverage и исходные
   candidate domains остаются как в H8. В reader передаются только
   реальные KG triples выбранных путей.

## Контрасты и метрики

- `H8`: только edge-to-edge contextual matching;
- `H9`: edge-to-edge или edge-to-path длины 2;
- `B1`: внешний retrieval baseline, не часть H9.

Primary retrieval metrics: overall path coverage, coverage по длине
1/2/3, non-empty evidence и число mappings, изменившихся относительно
H8. End-to-end metrics: Accuracy, Macro-F1, UNKNOWN и exact paired
McNemar/sign test по correctness. Также фиксируется среднее число
KG triples, чтобы не скрывать разницу evidence budget.

## Протокол решения

Текущие 500 dev claims использованы для вывода H9, поэтом на них
проверяется только механизм. Диагностический gate:

- H9 покрывает хотя бы один двухшаговый gold path;
- overall path coverage H9 выше H8 минимум на 5 п.п.;
- non-empty evidence H9 не ниже H8;
- потеря одношаговых gold paths относительно H8 не превышает
  прироста двухшаговых.

При прохождении gate все параметры замораживаются, а подтверждение
проводится на неиспользованных FactKG dev SHA-256 ranks 1000–1499.
До этого test split не используется. B1 не является порогом
прохождения диагностики: primary contrast — `H9 - H8`.

## Диагностический результат на 500 dev claims

Параметры из дизайна не менялись. H9 и H8 использовали одинаковые
query graphs, entity domains, KG pools, MiniLM encoder и beam width 64.

| Метод | Claims с evidence | Среднее triples/claim | Path coverage | Gold length 1 | Gold length 2 |
|---|---:|---:|---:|---:|---:|
| B1 | 481/500 | 19,186 | 416/767 = 54,24% | 387/517 | 29/242 |
| H8 | 178/500 | 0,458 | 219/767 = 28,55% | 219/517 | 0/242 |
| H9 | 245/500 | 0,826 | 239/767 = 31,16% | 231/517 | 8/242 |

H9 изменил best mapping для 53/500 claims. В сравнении с H8 он
добавил 12 одношаговых и 8 двухшаговых gold paths, не потеряв
ни одного path, который покрывал H8. Выбранные alignments включают
229 одношаговых и 96 двухшаговых KG paths.

Дополнительный oracle без изменения entity domains показал, что среди
всех допустимых между кандидатами путей имеются 278/517
одношаговых и только 20/242 двухшаговых gold paths. H9 выбрал
231/278 и 8/20 соответственно. Поэтом главное ограничение
двухшагового retrieval в этой версии — не отсутствие троек в KG pool,
а отсутствие правильных концов в исходных entity domains.

**Решение:** H9 прошёл проверку механизма, но не прошёл
заранее заданный gate по общему coverage. Прирост составил
`31,16 - 28,55 = 2,61` п.п. вместо требуемых 5 п.п. Reader и
независимая dev-выборка для этой версии не запускаются. Менять
штраф `0.1` после просмотра результа нельзя. Следующая версия
должна совместно решать endpoint linking и edge-to-path selection,
сравниваясь с H9 как с абляцией.

Локальные сырые артефакты: `data/evaluation/h9-dev-500-diagnostic/`.
