# Правила разметки и адаптации эталона

> Создан: 2026-10-29  
> Контекст: задача О11; входы — [О7](evaluation-protocol.md), [О10](data-format.md).

---

## 1. Единица оценки

Пилот оценивает качество **subgraph retrieval**: насколько точно метод извлекает из KG подграф, соответствующий эталонному answer-subgraph.

### 1.1 GTSQA

- **Единица оценки:** answer-subgraph — набор направленных рёбер `(head_id, rel_id, tail_id)` из поля `graph`.
- **Что оцениваем:** метод принимает `text` (вопрос) и возвращает набор рёбер; сравниваем с `gold_edges`.
- **Атомарный элемент сравнения:** ребро как тройка `(head_id, rel_id, tail_id)`.

### 1.2 FactKG

- **Единица оценки:** supporting subgraph — набор рёбер из поля `graph` + бинарная метка (`label: true/false`).
- **Что оцениваем:** метод принимает `text` (утверждение) и возвращает набор рёбер; сравниваем с `gold_edges` безотносительно метки.
- **Метка не входит в задачу retrieval:** `label` хранится в `metadata`, но не передаётся retrieval-методу и не используется как таргет при вычислении метрик subgraph retrieval.

## 2. Допустимые соответствия

### 2.1 Метрики сравнения

Сравнение ведётся как **нечёткое множество рёбер** по идентичности строк:

```
TP = |{e ∈ predicted} ∩ {e ∈ gold}|
precision = TP / |predicted|
recall    = TP / |gold|
F1        = 2 * precision * recall / (precision + recall)
```

Порядок рёбер не имеет значения. Граф оценивается как мультимножество: дублирующее ребро в predicted не считается повторным TP.

### 2.2 Множество допустимых ответов

- **GTSQA:** один канонический эталон на вопрос (поле `graph` из датасета). Альтернативных золотых ответов нет — если вопрос допускает несколько подграфов, датасет этого не отражает.
- **FactKG:** один эталонный граф (поле `graph`). Некоторые связи KG могут быть корректны семантически, но не входить в эталон — они **не считаются TP**.

### 2.3 Частичное совпадение

Частичное совпадение учитывается через F1 — метод не обязан извлечь весь подграф точно. Примеры с F1 > 0 считаются частично успешными при анализе, но пороговые решения (hit/no-hit) выставляются в [О12](../docs/evaluation-protocol.md) — не здесь.

## 3. Случаи неполного или отсутствующего эталона

### 3.1 Правило «отсутствие записи ≠ отрицательная метка»

Если ребро отсутствует в `gold_edges`, это означает, что оно **не задокументировано в эталоне**, а не то, что в KG этой связи нет. Retrieval-метод, нашедший реальную, но не размеченную тройку, получает FP — это ограничение датасета, не ошибка метода.

### 3.2 Пустой подграф в GTSQA

Если поле `graph` в исходном файле пустое (пустой список или пустой dict) — пример исключается с причиной `"empty_gold"`. Такой пример **не поступает в evaluator** и отмечается в `gold-audit.md`.

### 3.3 FactKG test-split

Тестовый split FactKG не содержит поле `graph`. `load_factkg(..., Split.TEST)` бросает `ValueError`. Тестовый split FactKG **не используется в пилоте**.

### 3.4 Неизвестный ответ (тип Existence в FactKG)

Примеры типа `"Existence"` могут иметь минимальный supporting graph (одно–два ребра), которые не исчерпывают возможные подтверждения. Такие примеры **не исключаются** — они получают статус `"evaluable"`, но в `gold-audit.md` помечаются как `"thin_gold"` для отдельного анализа результатов.

## 4. Правила спорных случаев

| Ситуация | Решение | Статус примера |
|----------|---------|----------------|
| `graph_isomorphism = null` или пустое в GTSQA | исключить | `excluded` / `"null_type"` |
| Пустой граф (`gold_edges = []`) | исключить | `excluded` / `"empty_gold"` |
| FactKG `Existence` с ≤1 ребром | не исключать, пометить | `evaluable` / `"thin_gold"` |
| ID примера не уникален в split | остановить загрузку с ошибкой | — |
| `graph` = `None` | исключить | `excluded` / `"none_gold"` |
| `text` пустой или только пробелы | исключить | `excluded` / `"empty_text"` |
| Дублирующийся `text` в FactKG (разные claims, одинаковый текст) | оставить оба, зафиксировать в аудите | `evaluable` / `"dup_text"` |

**Ключевое правило:** исключения фиксируются **до начала оценки методов** и не меняются по результатам работы метода.

## 5. Критерии исключения из оценочной выборки

Пример исключается из финального `gold.jsonl` (статус `"excluded"`) при выполнении **любого** из условий:

1. `gold_edges` пуст или `None` после парсинга адаптером.
2. `text` пуст или состоит из пробелов.
3. `graph_isomorphism` равен `null` (только GTSQA).
4. Пример принадлежит FactKG test-split.
5. Пример помечен вручную в ходе аудита как ошибочно размеченный (с фиксацией обоснования).

Примеры со статусом `"unknown"` — те, где ответ в KG не может быть однозначно подтверждён или опровергнут — **остаются в золоте** с пометкой, но исключаются из финального агрегированного числа «оценимых».

## 6. Формат `data/evaluation/gold.jsonl`

Каждая строка — JSON-объект:

```json
{
  "id": "gtsqa-test-0001",
  "source": "gtsqa",
  "split": "test",
  "text": "What is the capital of France?",
  "gold_edges": [
    {"head_id": "Q142", "rel_id": "P36", "tail_id": "Q90",
     "head_label": null, "rel_label": null, "tail_label": null}
  ],
  "metadata": {
    "answer": "Paris",
    "graph_isomorphism": "single-hop",
    "n_hops": 1
  },
  "audit_status": "evaluable",
  "audit_note": null
}
```

Поле `audit_status`: `"evaluable"` | `"excluded"` | `"unknown"` | `"thin_gold"`.  
Поле `audit_note`: строка с причиной для нестандартных случаев; `null` для `"evaluable"`.

Файл генерируется скриптом `scripts/build_gold.py`. Не коммитится (находится под `.gitignore`).

## 7. Независимость тестовой выборки

- Примеры, просмотренные при отладке адаптера (fixtures в `tests/fixtures/`), идентифицированы как синтетические — они не входят в реальные датасеты.
- При ручном аудите не допускается выбор исключаемых примеров на основании предсказаний retrieval-метода.
- Если в ходе аудита потребовалось изменить правило исключения (что-то не учли), правило фиксируется в §4, все примеры пересчитываются по новому правилу единообразно.
