# Требования к данным и критерии выбора

> Последнее обновление: 2026-10-24  
> Контекст: задача О3, входные данные — научный статус из [О1](https://github.com/OlegYurchik/soft-isomorphism/issues/1).

---

## 1. Исследовательские вопросы

### Q1 — Основной: когда структурный учёт помогает при сопоставлении?

В каких условиях мягкое структурное сопоставление (soft isomorphism между графом документа и KG) находит правильные подграфы лучше, чем:

- **Базис A**: поиск без структуры (text-only similarity по сущностям);
- **Базис B**: строгое изоморфное сопоставление (exact subgraph match).

Отдельный вопрос, **не входящий в эту задачу**: улучшается ли конечное обнаружение противоречий (fact verification). Q1 — про качество сопоставления графов, а не про downstream-задачи.

### Q2 — Вспомогательный: что делает случай «нетривиальным»?

Когда структурные ограничения в документе существенны? Гипотезы: multi-hop отношения, нелинейная структура (не цепочки), несоответствие поверхностных форм при совпадении структуры.

## 2. Схема оценки

```
Вопрос → Вход → Единица оценки → Эталон → Метрика
```

| Элемент | Описание |
|---------|----------|
| **Вход** | Документ с именованными сущностями и отношениями (document graph); KG с теми же сущностями и отношениями |
| **Единица оценки** | Субграф KG, сопоставленный с document graph (не отдельная сущность, не QA-пара) |
| **Эталон** | Размеченное соответствие: какой подграф KG является правильным ответом для данного document graph |
| **Метрика (Q1)** | Precision/Recall@k по совпадению рёбер и узлов в top-k retrieved подграфах; MRR |

### Уровни разметки и достаточные условия

| Уровень | Что нужно | Достаточно для Q1? |
|---------|-----------|-------------------|
| Сущности | Аннотированные упоминания → KG-IDs | Нет (без отношений структура не проверяется) |
| Утверждения (triplets) | Сущности + тип отношения + направление | Да (минимально достаточно) |
| Подграфы | Аннотированные multi-hop пути / кластеры | Да (предпочтительно для нетривиальных случаев) |

## 3. Обязательные условия (must-have)

Все четыре условия должны выполняться одновременно:

1. **Доступность файлов и лицензия**: данные должны быть публично скачиваемы без регистрации или с открытой лицензией (CC-BY, MIT, Apache 2.0 или аналог). Проприетарные датасеты и данные Synapse не рассматриваются.
2. **Воспроизводимые идентификаторы**: KG должен содержать стабильные URI или числовые ID сущностей и отношений; документы — уникальные ID примеров. Необходимо для воспроизводимых экспериментов.
3. **Подходящая разметка**: датасет должен содержать явную связь сущность-документ → KG-ID и хотя бы уровень utverzhdeniy (triplets). Наличия только текстовых ответов недостаточно.
4. **Независимый источник query graph**: датасет должен содержать document graph/query graph либо предоставлять текст, из которого его можно построить зафиксированным методом без использования gold answer/path/evidence. Gold subgraph допускается только в evaluator-е. Отдельно фиксировать, если query graph синтетически получен из gold для stress test.
5. **Разделение поиска и оценки**: явно определить candidate KG/corpus, способ построения candidate pool и gold evidence; данные gold не должны попадать в candidate generator или matcher.
6. **Независимая верификация**: способ проверить правильность ответа без проприетарной системы; эталон должен быть в публичном файле датасета.

## 4. Желательные свойства (nice-to-have)

| Свойство | Зачем |
|----------|-------|
| Multi-hop отношения (глубина ≥ 2) | Нетривиальные структурные случаи для Q2 |
| Нелинейные графы (не только цепочки) | Тест на subgraph matching, а не path matching |
| Несколько доменов | Проверка обобщаемости подхода |
| Размер пилота < 10K примеров | Позволяет ручную проверку и быстрые итерации |
| Пересечение benchmark с аналогом | Позволяет сравнить на одном наборе (например, HotpotQA для NGM-RAG, MetaQA для SimGRAG); не заменяет воспроизведение общего pipeline |
Поддержка Wikidata или Freebase | Совместимость с KG-инструментами экосистемы |

## 5. Ресурсные ограничения и допустимая подготовка

| Ресурс | Ограничение |
|--------|-------------|
| Вычисления | CPU или единственный GPU (≤24 GB VRAM); без кластера |
| Хранилище | ≤ 50 GB для полного датасета и промежуточных файлов |
| Время адаптации | ≤ 4 ч на загрузку + preprocessing; ≤ 2 ч ручной проверки выборки |
| LLM-доступ | Не считается гарантированным; методы с обязательным API GPT-4+ исключаются как baseline |
| Разметка | Нет бюджета на ручную аннотацию; только готовые или автоматически производные эталоны |

Если подготовка датасета требует > 4 ч или специального доступа — фиксируем как ограничение при выборе, но не исключаем автоматически.

---

## 6. Критерии исключения кандидата

Критерии применяются **до** просмотра результатов собственного метода на этом датасете.

| Критерий | Обоснование |
|----------|-------------|
| Нет KG-backing (text-only) | Невозможно построить document graph → KG match |
| Только оценка сущностей без отношений | Q1 требует структурного сопоставления; entity linking — недостаточно |
| Проприетарная лицензия или недоступные файлы | Нарушает обязательное условие #1 |
| Не воспроизводимые ID (нестабильные ссылки) | Нарушает обязательное условие #2 |
| Правильный ответ требует reasoning вне структуры графа | Не позволяет изолировать вклад структурного сопоставления |
| Оценка сущностей используется как прокси для качества утверждений | Явно не должно происходить: entity match ≠ claim match |

## 7. Проверка утечки и контракта входа (дополнение 05.11.2026)

До выбора датасета заполнить контракт каждого experiment: `query source → graph extractor → candidate corpus/KG → candidate generator → matcher → evaluator-only gold → primary metric`. Поля search graph, query graph и gold graph должны быть отдельными и трассируемыми до исходного поля.

Если датасет содержит только question + answer_subgraph, это не означает, что answer_subgraph можно использовать как query. Это допустимо только в отдельном контролируемом алгоритмическом stress test (например, искусственно удалить часть gold-рёбер), с отдельным выводом и без заявления end-to-end document graph retrieval.
